# 开发包启动被终止，源码入口可运行

## 状态与影响

- 发现日期：2026-10-21。
- 严重程度：P1，阻塞当前机器上的 `.app` 日用验收，不阻塞源码编译和开发入口测试。
- 状态：**尚未确认系统终止进程的直接原因，未宣称修复。**
- 修复 commit：不适用；本记录随初始工程提交保存。
- 影响范围：本机生成的 ClipDune 开发应用包；不能外推到其他机器、签名证书或正式公证包。

## 0.2.0 验证更新

2026-10-21 后续构建中，0.2.0 Release 应用包通过了普通／原生全屏 GUI 检查。测试宿主保持为 SwiftPM 开发入口，**被测 ClipDune 本体来自 `dist/ClipDune.app`**，不是拿未打包应用替代。

中间一轮 bundle QA 在临时包装的测试宿主启动时被终止，尚未执行被测应用；现已移除不必要的测试宿主打包步骤。这个事实不能证明 0.1.0 当初被终止的根因，但说明不能把测试宿主终止当作 0.2.0 应用启动失败。

本记录保留历史证据；当前 0.2.0 不再被标为“应用包未能启动”，后续仍需正式签名公证和真实终端验收。

## 现象与已验证证据

1. SwiftPM Debug 编译通过，自包含测试与未打包的图标生成入口运行通过。
2. 首次在资源尚未组装完整时执行复制后的二进制，签名验证提示 `code has no resources but signature indicates they must be present`。
3. 完整签名后，`codesign --verify --strict` 返回成功，但应用包内可执行文件仍被终止，shell 返回 `137` / `Killed: 9`。
4. 通过系统 `open` 提交启动请求返回成功，但预期的图标输出没有产生；提交成功不等于应用实际完成运行。
5. 换新文件 inode、重新签名、保留工具链已有开发 entitlement 的对照实验，均未解决包启动问题，因此停止这些方向的重复尝试。
6. 相同程序的 SwiftPM 开发入口运行成功；普通与原生全屏隔离 GUI 检查也通过。这是对运行入口差异的证据，不是包启动已经修复的证据。

## 定位边界

只读系统日志出现了代码签名评估与企业终端防护的进程标签事件。但同类签名评估也出现在能够成功运行的测试程序中，进程标签事件本身没有证明是谁发送终止信号。

因此目前只能确认：**磁盘签名有效，不代表该机器一定允许应用包运行**。不能把原因直接写成“AppKit 崩溃”“企业防护拦截”或“签名缓存错误”。

## 本次调整

- 构建顺序改为：编译 → 使用编译产物生成图标 → 组装完整资源 → 应用包签名 → 验证磁盘签名。
- UI 检查明确分成 `development` 与 `bundle` 两个入口，结果不可互相替代。
- 没有关闭 Gatekeeper、终端防护、系统完整性保护，没有清除权限数据库，也没有伪装其他应用身份。

## 下一步安全验证

在可正常运行自建开发应用的环境，或经设备管理方确认允许的签名／发行方式下，执行 `bash scripts/check-ui.sh bundle`，保留应用包启动及 GUI 结果。若当前设备需要管理方处理，提供无剪贴板正文的 PID、时间和签名诊断，不自行更改安全策略。

## 避免误判

- 不把编译成功、签名验证成功、LaunchServices 请求成功和 GUI 验收成功合并为一个“通过”。
- 功能测试只使用独立命名剪贴板和合成内容。
- 不因终止信号名称或同一时刻某进程出现在日志里就宣布根因。
