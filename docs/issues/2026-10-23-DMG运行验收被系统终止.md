# 双架构 DMG 的复制后运行验收被系统终止

- 发现日期：2026-10-23。
- 严重程度：P1，阻断正式发布；未涉及用户历史数据或已安装应用的修改。
- 影响范围：本机在新路径运行的 ClipDune 开发签名包。不能据此判断所有 Mac 或所有 Intel／Apple Silicon 包都无法运行。
- 状态：终止根因未确定；0.4.1 仅准备草稿，线上保持 0.4.0。
- 相关实现 commit 可通过 `git log --all --grep='构建双架构 DMG 并阻断未验收发布'` 定位。

## 现象与可重复检查

`bash scripts/check-dmg.sh dist/release-0.4.1/ClipDune-0.4.1-macOS-arm64.dmg arm64 --smoke` 可以通过镜像校验、挂载、版本、公钥、单架构和严格代码签名检查，但执行镜像内应用的 `--render-icon` 后收到 `SIGKILL`，退出码 137，没有生成图标输出。

该入口在创建 AppDelegate 前结束，不读取真实系统剪贴板或用户历史。运行测试不能只依据 `codesign` 或 `open` 的退出状态。

## 对照实验

| 对照 | 结果 |
| --- | --- |
| 原位置 `dist/ClipDune.app` 的 Universal 包 | 图标输出成功，退出 0 |
| 字节相同的 Universal 主程序随应用复制到临时目录 | 退出 137，无图标输出 |
| ARM 单架构包直接在 DMG 内运行 | 退出 137 |
| 同一个 ARM 包复制到临时目录、项目的独立诊断目录 | 均退出 137 |
| 提取切片并保留原签名，不再重新签名 | 静态签名通过，启动仍退出 137 |
| 已发布的 0.4.0 包从 GitHub 下载到临时目录后运行 | 同样退出 137 |
| 编译器直接生成的原生 ARM 可执行文件 | 图标输出成功，退出 0 |
| 使用 LaunchServices `open` 启动复制后的包 | 启动请求返回，但没有实际图标输出，不能算通过 |

这些结果排除了“只因 DMG 只读挂载”“仅新版本业务代码变化”“仅提取切片后重新签名”作为充分解释。复制的 Universal 主程序与原文件逐字节相同，权限相同，未发现 quarantine 等扩展属性。

## 定位边界

系统日志中的 ad-hoc／未知证书链评估也出现在成功运行的程序上，不能据此直接断定终止发起方。本机没有可用的 Developer ID Application 签名身份；也没有可用的 Intel 执行环境。尚未确认是平台执行策略、设备管理策略还是其他本机因素。

没有关闭 Gatekeeper、企业防护或系统完整性保护，没有清除权限／信任数据库，没有更改应用身份冒充其他程序，也没有安装 Rosetta。

## 构建与发布保护

1. 构建、静态封装校验和运行验收分开：`make release`／`prepare` 生成两个 DMG、Universal ZIP、签名清单及校验文件；`draft` 下载后再次做静态验证。
2. `publish` 必须通过 Universal 包 GUI 检查及本机架构 DMG 的实际渲染启动检查。运行失败时不得晋升 Latest；草稿不能被在线更新器消费。
3. Intel 包必须明确标注“交叉编译和静态检查通过，尚未 Intel 实机验收”，不能把 ARM 上的检查等同于 Intel 运行。
4. 本机 `lipo` 的多架构 `-verify_arch` 调用报“requires exactly one input file”，尽管帮助展示多个架构参数。逐个验证 arm64、x86_64 均通过，因此构建脚本分别验证主程序和辅助程序的四个切片，不跳过校验。
5. 临时挂载卸载失败时做有限重试，仍失败则报告挂载点，不强制结束无关进程。

## 后续安全验收

在允许正常运行自建开发签名应用的环境，或采用合法 Developer ID 签名的流程后，重跑实际 DMG 的运行检查，并在 Intel 机器补充运行验收。完成以前保留草稿，不通过移除运行检查或修改安全策略来冒充验收通过。
